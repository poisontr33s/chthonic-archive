# Research Brief for the Chthonic Scanner Rust Port

## Executive recommendations

Rust is worth doing here, but not for the simplistic reason that “Rust will obviously hash and walk faster than Bun.” On the hashing side, Bun’s `createHash()` path is already native and Bun documents `CryptoHasher` as hardware-accelerated with BoringSSL. BoringSSL’s Windows x86_64 SHA-256 implementation includes a hardware path using SHA extension instructions such as `sha256rnds2`, `sha256msg1`, and `sha256msg2`, while RustCrypto’s `sha2` detects x86 SHA support at runtime and offers assembly backends. In other words, the CPU-side SHA-256 contest is already between native, accelerated implementations on both sides, so the raw hashing gain from the port is likely to be modest rather than dramatic. citeturn1search4turn59search7turn7view0turn7view1turn8search5turn9view0

The strongest reasons to port are elsewhere: a tighter native integration path for the VS Code extension, more controlled parallelism for walking and hashing, a better runway for persistent indexing, and a cleaner substrate for Tree-sitter and GPU compute later. For the walker itself, the best current default is `ignore::WalkBuilder` with the standard filters disabled, because it gives you a parallel walker, tunable threads, and production-grade traversal machinery without forcing `.gitignore` semantics if you explicitly turn those filters off. `walkdir` remains the safest simple baseline, but it is single-threaded; `jwalk` is compelling when you want sorted streamed results and per-directory preprocessing, but its own docs frame its biggest wins around sorted traversal and deep trees, and its latest release is older than the `ignore` line. citeturn13view0turn12search1turn12search2turn14view0

For magic-byte detection, the most pragmatic pick is **`file-format` plus a thin custom rule layer** for the scanner’s domain-specific cases. `file-format` is pure Rust, covers a wide range of signatures, and can optionally use format-specific readers for ZIP, XML, PDF, SQLite, and related families. `infer` is lightweight and easy to extend, but its built-in surface is noticeably narrower. `tree_magic_mini` is smart and fast for MIME detection, but it is tied to the freedesktop shared MIME database and its embedded-database route carries GPL implications. `libmagic` still has the broadest ecosystem gravity, but it brings a native dependency, Windows packaging friction through `vcpkg`/system libraries, and the longstanding parser complexity that has produced many memory-safety bugs and CVEs. citeturn20view0turn21search0turn42view0turn43view0turn43view1turn24search5

For caching, **keep NDJSON for the current 50k-row scale** and only move to SQLite when the cold-start parse cost becomes visible at substantially larger scales or once the scanner becomes a persistent service. SQLite explicitly positions itself as a local-storage system that “competes with `fopen()`,” WAL mode is persistent, and SQLite’s own measurements show that for many small blobs it can outperform filesystem-per-file access. That makes SQLite the right next cache step when you outgrow text-row scanning, but not the obvious first move at your present scale. A custom binary format is lower on the priority list than it might look because `bincode` and MessagePack already buy you “compact binary” without locking you into a bespoke file format that only your scanner can debug. citeturn17search0turn17search2turn17search16turn18search0turn18search1turn18search3

For V2.3 and V2.4, the substrate choices are already fairly clear. **Tree-sitter** is the right base for symbol extraction because it is incremental, robust to syntax errors, and has official Rust bindings plus upstream parsers for several of your core languages. For MinHash, **`probminhash`** is the strongest “correctness-first” pick among the crates you named because it implements published Ertl-family algorithms and related sketching methods, whereas `probabilistic-collections` and `minhash-rs` stay closer to straightforward classic MinHash. For GPU acceleration, **`wgpu` with custom WGSL compute shaders** is the durable route; I did not find a broadly established general-purpose Rust MinHash GPU stack on the level of `wgpu` itself, even though niche crates now exist that advertise GPU MinHash in narrower domains. citeturn53view0turn51search6turn55view0turn55view1turn56search1turn56search2turn56search6turn58search2turn58search3turn58search10turn58search12

## Performance reality check

The most important bias to kill early is the idea that Rust will provide an order-of-magnitude win on SHA-256. It probably will not. Bun’s `createHash` path is native, Bun documents it as hardware-accelerated with BoringSSL, and BoringSSL’s Windows x86_64 assembly clearly includes a hardware SHA-256 path. RustCrypto’s `sha2` also detects x86 SHA support at runtime and offers assembly support. The practical implication is that **a direct Bun-vs-Rust SHA-256 benchmark on a Windows 11 x64 SHA-NI machine is likely to be a single-digit to low-tens-percent contest, not a 3x–10x rewrite justification**. If you see a materially larger win, it will most likely come from pipeline design around hashing rather than from the compression rounds themselves. OpenSSL-class SHA-256 implementations on modern x64 machines commonly land in the roughly sub-GB/s to low-single-GB/s range depending on block size and continuous streaming conditions, which is already in the same ballpark as local storage throughput for medium and large files. citeturn1search4turn59search7turn7view0turn7view1turn8search5turn9view0turn11search1turn11search10

Directory walking on NTFS is even more clearly an I/O and metadata problem. The Win32 enumeration API does not sort results for you, which means any higher-level stack is still standing on top of metadata fetches and directory enumeration. `walkdir` gives you a solid single-threaded baseline; `ignore` adds a production-ready parallel walker; `jwalk` explicitly says its biggest benefit appears when you want streamed sorted output and when the tree is deep enough that directory-level parallelism helps. That means **the realistic Rust gain over Bun for a 50k-file cold walk is probably “small-to-moderate,” not “night and day,” and it will shrink further on warm metadata caches**. If the benchmark is a warm-cache rerun with a very high file-index hit rate, you should expect much of the remaining wall-clock time to sit in metadata checks, cache parsing, and a comparatively small number of content reads. citeturn12search15turn12search2turn12search1turn13view0turn14view0

The storage floor matters more than language choice once files stop being tiny. For small files, effective throughput is governed by random I/O and metadata churn, not headline sequential throughput. Even consumer-oriented storage guidance keeps emphasizing that the big HDD-to-SSD jump came from random I/O, while the SATA-to-NVMe jump is much smaller on 4K random reads than on sequential bandwidth. That means a scanner chewing through **50,000 tiny files will often behave like a random-I/O workload with effective throughput in the tens to low hundreds of MB/s**, while **1 MB-class files can move into the hundreds-of-MB/s to low-GB/s regime**, and **tens-of-MB files can approach sequential-drive behavior until CPU hashing catches up**. Said differently: on your hardware, the cold path for a poly-repo scan is mostly bounded by storage behavior and filesystem metadata patterns, not by whether the loop is written in TypeScript or Rust. citeturn59search0turn59search4turn11search1turn11search10

Bun is therefore already “good enough” for two parts of the current design: **full SHA-256 of medium/large files** and **NDJSON cache handling at roughly 50k rows**. The Rust port should not chase those first. The port should instead focus on the pieces where Rust unlocks structural improvements: bounded parallel walking, bounded parallel hashing, a better long-lived service model, richer content classification, and the future Tree-sitter/GPU lane. citeturn1search4turn59search7turn17search0turn18search0turn18search3

## Hashing and duplicate strategy

The best exact-duplicate design for V2.2.5 and later is not “full SHA-256 for every file under 50 MB,” but **size bucketing first, then a cheap sampled fingerprint, then full SHA-256 only inside candidate buckets**. The canonical shape for this scanner is straightforward: group by file size, skip full hashing for singleton sizes, and for non-singletons compute a small sampled digest over fixed windows such as the first 4 KiB, a middle 4 KiB, and the last 4 KiB, with the file size included in the sampled fingerprint. Only when that sampled digest collides do you pay for full streaming SHA-256. This is an engineering recommendation rather than a standard library requirement, but it maps cleanly onto the scanner’s workload because exact duplicates must share size, and most unique files become singletons very early. The real risk in the sampled stage is not cryptographic collision of the digest function; it is **sample aliasing**, where two different files happen to share identical bytes at the sampled offsets. That risk is corpus-dependent, so the right way to validate it is to count how often sampled collisions survive into unequal full hashes on your own workspace. citeturn1search4turn59search7turn8search5turn9view0

For files that do require full hashing, **prefer buffered streaming reads over `memmap2` as the default path**. Memory mapping is not “faster file I/O” in some magical absolute sense; it is a virtual-memory mechanism in which the file is mapped into address space and pages are brought in on demand. That can be excellent when you will revisit the data, randomly probe it, or share access patterns across components, but a one-pass linear hash over 1–50 MB files is usually better served by a large reusable read buffer plus streaming digest updates. The memory-mapped option is still worth keeping behind a feature flag for experiments on large, repeatedly re-read assets or later symbol/format parsers, but it should not be the default complexity you carry into the first Rust port. citeturn59search1turn16search6turn59search13

Parallel hashing should also be **bounded**, not maximized. SSDs are fast enough that a little parallelism helps, especially when the work mixes metadata waits, open calls, and digest updates, but you do not want a naive `rayon::par_iter()` unleashing unlimited small-file reads against a single device. The right starting point is a small worker pool—typically 2 to 4 concurrent file readers on a single local NVMe drive—then a benchmark sweep at 1, 2, 4, and 8 workers for three datasets: many tiny files, medium 1 MB-class files, and large files. The expected result is that **small-file throughput peaks quickly and can get worse with too much concurrency**, while medium and large files benefit somewhat more before flattening. That recommendation is an inference from the random-I/O ceiling and the walker crates’ parallelism model, not a claim that one universal thread count fits every SSD. citeturn13view0turn12search1turn59search0turn59search4

If you need a single concrete answer for the SHA-256 benchmark expectation, this is the one I would plan around: **Rust itself is unlikely to beat Bun by more than roughly 0%–25% on the raw SHA-256 kernel on a modern Windows x64 host with SHA acceleration**, and it may be effectively tied. **End-to-end cold-run wins can still reach “noticeable” territory if the Rust pipeline improves walking, batching, and candidate reduction**, but the port should not be justified on the hash primitive alone. citeturn1search4turn59search7turn7view0turn7view1turn8search5turn9view0

## Magic detection canon

The best magic-detection answer for this scanner is **not** “pick one library and delete the hand-rolled rules.” The best answer is: **pick `file-format` as the base classifier, keep a compact scanner-owned overlay for the niche artifacts you care about, and use extension-aware text heuristics where magic bytes are the wrong abstraction**. `file-format` is pure Rust, detects a broad range of signatures, has optional readers for families such as ZIP, XML, PDF, and SQLite, and falls back cleanly to generic binary when it cannot identify a signature. That makes it a better fit than `infer` for your mixed corpus, because `infer` is intentionally small and its current built-in map does not surface ONNX, GGUF, SPIR-V, or safetensors support. citeturn20view0turn21search0turn31view0turn31view1turn31view2turn31view3turn37view2turn37view3turn37view4

`tree_magic_mini` is the most interesting alternative if your priority is MIME-style classification accuracy across a broad desktop corpus. Its design goal is to reduce false positives relative to older `libmagic`-style blanket checking by organizing known MIME types in a type tree, and it can load the freedesktop shared MIME database at runtime or embed it through `tree_magic_db`. The problem for your scanner is that this pushes you into a MIME-database distribution story, and if you embed the database the crate documentation explicitly warns that the database files are GPL-licensed. That is a material architectural and licensing consideration for a Windows-first extension-integrated native crate. citeturn42view0turn40search0turn40search15turn40search18

`libmagic` remains the “broadest, most familiar” ecosystem choice, but it is the wrong default here. The Rust bindings require the C `libmagic` library, use `pkg-config` or `vcpkg` to locate it, and the Windows path is explicitly documented through `cargo-vcpkg` or external installation. On top of that operational burden, `libmagic`’s parser surface has a long security history; Trail of Bits notes that it includes many manually written parsers that have led to numerous memory-safety bugs and CVEs. For a scanner that is already happy to own some purpose-built detection logic, that trade is hard to justify. citeturn43view0turn43view1turn24search5

The place where the custom overlay earns its keep is the exact set of formats you named. **GGUF** is a specific binary model format with its own formal documentation; **SPIR-V** binaries have a stable magic number of `0x07230203`; **PyTorch `.pt` / `.pth` artifacts** are frequently ZIP-based in modern PyTorch serialization; and **ONNX** is an open model format built on protobuf structure rather than on a universally distinctive “single magic signature” story. No mainstream Rust magic crate currently gives you a scanner-perfect out-of-the-box answer across that cluster. What you want instead is a small first-party rule table for: SPIR-V magic, GGUF magic/header checks, ZIP-plus-internal-layout checks for PyTorch archives, and extension-plus-structure validation for ONNX. citeturn23search0turn23search2turn24search8turn24search12turn24search3turn24search15turn23search1turn23search7turn23search18

That also answers the Unity question indirectly: files like `.meta` and `.asmdef` are better handled as **extension-specific text/config classification** than as magic-byte problems. In practice, your classifier should first decide whether a file is a text/config candidate, and only then ask a magic library to help on genuinely binary or ambiguous payloads. That keeps the “magic” subsystem focused on the problem it actually solves. citeturn20view0turn42view0

## Cache and walking architecture

At today’s scale, **NDJSON is still the right cache format**. It is easy to inspect, easy to repair, append-friendly, and already aligns with the scanner’s “one row per file” model. The engineering breakpoint for moving to SQLite is not “50k rows exist”; it is “cold cache load is now observably expensive” or “the scanner has become a persistent process with richer incremental update semantics.” SQLite’s own positioning as local storage that “competes with `fopen()`,” plus WAL’s persistence and the documented filesystem-vs-SQLite small-blob result, make SQLite the right durability step when the cache grows into the low millions of rows or the service model becomes more sophisticated. Before that point, the main thing SQLite buys you is structure, not transformational speed. citeturn17search0turn17search2turn17search16

If and when you do cross that line, the schema should stay boring: one row per path with `path`, `size`, `mtime`, `quick_fp`, `sha256`, `bucket`, `kind`, `magic_kind`, and `project_root`, plus indexes on `path` and `(size, quick_fp)`. That gives you efficient invalidation and candidate lookup without turning the cache into a database project. You do not need content-addressed remote-cache machinery in the Bazel or `sccache` sense unless the scanner starts shipping or reusing content blobs across machines. For this scanner, the useful content-addressing pattern is local and narrow: reuse full hashes and duplicate-cluster results, not remote artifact transport. SQLite makes that evolution easy; a bespoke binary format does not. citeturn17search0turn17search2turn18search0turn18search1

A custom binary format is therefore **not worth the implementation cost yet**. `bincode` gives you a compact “zero fluff” binary encoding and MessagePack via `rmp-serde` gives you a compact structured binary format with stream-writing support. Either one is a reasonable future compression layer if you decide the human-readability of NDJSON is no longer worth its size and parse overhead. Rolling your own fixed-width records plus path table would move complexity into versioning, corruption recovery, and tooling without giving you a unique strategic advantage. citeturn18search0turn18search1turn18search3turn18search16turn18search19

For cache layout, **split per project root** once you move beyond the current footprint. That is the cleanest way to parallelize load and write, and it matches how the scanner already thinks about inventories. The tradeoff is that duplicate detection remains a workspace-level reduction step, so you still want a final aggregate pass that merges `(size, quick_fp, sha256)` across project caches into the duplicate-cluster map. This is exactly the kind of decomposition Rust is good at: let per-root tasks stay embarrassingly parallel, then do one bounded reduction phase. That recommendation is a design inference built on the walker and cache behavior above. citeturn13view0turn17search0turn17search2

For the walker itself, the concrete pick is **`ignore::WalkBuilder` configured to disable the standard ignore filters**. The crate documents a parallel walker, configurable thread count, and a single switch to disable hidden-files and ignore-file behavior as a group, with the option to re-toggle individual filters if needed. That gets you a ripgrep-grade traversal core without violating the directive to ignore `.gitignore` semantics. Keep `walkdir` around as the correctness baseline for benchmarks and tests. Reach for `jwalk` only if you later decide that sorted streamed output or per-directory preprocessing at traversal time is a first-class feature, because that is where its own documentation claims the standout speedups. citeturn13view0turn12search1turn12search2turn14view0

## V2.3 and V2.4 substrate decisions

Among the MinHash-family crates you named, **`probminhash` is the strongest correctness-first foundation**. Its docs and repository explicitly tie the implementation to published work by Otmar Ertl and expose more than one family of sketching algorithms, including ProbMinHash, SuperMinHash, SetSketch, and densification methods for One Permutation Hashing. By contrast, `probabilistic-collections` offers a classic MinHash and shingle iterator with a simpler interface, and `minhash-rs` presents a straightforward MinHash implementation with much less visible algorithmic depth. If your priority is “use the most serious sketching substrate and build the scanner’s own bucket/index layer around it,” `probminhash` is the right call. If your priority were only “ship a textbook MinHash demo quickly,” the other two would be easier. citeturn55view0turn55view1turn56search1turn56search2turn56search6turn56search8

For source-code near-duplicate detection specifically, I would start with **normalized token shingles rather than raw byte shingles**. Normalize away comments and cosmetic whitespace, optionally normalize identifiers and literals into placeholders, then build **5-token shingles**, sketch them with **128 hashes**, and start with a **Jaccard threshold around 0.85** for “strong near-dupe” candidates. That exact parameter triple is an engineering recommendation rather than a universal standard, but it aligns well with classic shingling-based similarity logic and gives a practical balance between recall and false positives for code. Keep the existing exact-duplicate SHA-256 path beside it; MinHash should expand the salvage classifier, not replace exact duplicate semantics. The underlying literature around shingling, MinHash, and fingerprinting is the right theoretical base, but these exact thresholds should be tuned on your own corpus. citeturn54search4turn54search9turn54search14turn57view0

For symbol extraction, **Tree-sitter is the correct substrate**. The project’s own introduction emphasizes that it is incremental, fast enough to parse on every keystroke, and robust in the presence of syntax errors. The official Rust bindings are current, and the upstream organization already maintains parsers for several of your core languages, including Rust, C, C++, C#, Python, JavaScript, TypeScript, HTML, and JSON, with many more grammars available through the broader ecosystem. That is a much better long-term fit than regex extractors if you want top-level declarations rather than loose heuristics. Regex remains useful as a fallback for fringe formats and for quick lexeme counting, but not as the main V2.3 symbol layer across 15+ languages. citeturn53view0turn51search6turn51search17

On GPU acceleration, the right assumption is that **you will probably write custom WGSL compute kernels**. `wgpu` is the stable cross-platform Rust compute/graphics API, runs natively on Vulkan, Metal, D3D12, and OpenGL, and exposes native-only subgroup features on Vulkan, D3D12, and Metal that are relevant to reduction-heavy workloads. That is exactly the toolchain you want if the GPU path must coexist with your existing Vulkan-oriented native workspace and remain portable inside a desktop extension environment. I did find niche evidence of Rust crates advertising GPU MinHash, but not a clear mainstream, battle-tested general-purpose MinHash GPU substrate that would let you skip writing the compute kernels yourself. For this scanner, GPU only becomes interesting once tokenization and sketch generation dominate wall-clock time; it will not rescue small-file directory walking or storage-bound full-file hashing. citeturn58search2turn58search3turn58search10turn58search12turn58search21

For continuous indexing, the canonical pattern is **watchers plus reconciliation**, not watchers alone. The `notify` docs explicitly warn that editors emit different save patterns and that very large directory watching can miss events; `notify-debouncer-full` exists to provide debounced event streams with a built-in file ID cache. That points to a robust architecture for an eventual extension lane: use `notify` for low-latency event capture, debounce and collapse events, update the per-project cache incrementally when events are straightforward, and schedule a periodic lightweight reconciliation walk to repair any missed or ambiguous changes. In a scanner that must be trustworthy, watcher-only correctness is too brittle. citeturn51search0turn51search4turn59search2turn59search14
