```
14.5. Adaptive Assessment Systems and Cluster-Based Heuristics

Goal: Formalize the practice of adaptive assessment — ore ratings that evolve based on cumulative observations.

Canon Rule:
  ALL assessment systems MUST be adaptive. No ore value, risk rating, or priority score is "final."
  Baseline ratings are hypotheses; they are refined through measured observation of outcomes.
  
Mechanism:
  1. Cluster profiling: Group assessed items by category (e.g., backup, candidate, recovered, legacy).
  2. Aggregate statistics: Track avg_ore, avg_extractable, yield_rate per cluster.
  3. Dynamic downgrade: When assessing a new item in cluster C, adjust baseline ore using cluster_avg.
  4. Learning rate: Each new assessment updates cluster statistics.
  
Example (Zombie Consumer):
  - Baseline ore for candidate file: 3/5
  - Cluster "candidate" has learned avg_ore from 29 samples: 1.0
  - Actual ore assigned: 3 × (1.0 / baseline_avg) = downgraded to 1
  - Next candidate in this cluster: baseline ore is now 1, not 3
  
Constraint:
  Adaptive heuristics MUST log their logic. Every assessment includes:
    - baseline_ore (hypothesis)
    - cluster_influence (if applicable)
    - adjusted_ore (final)
    - reasoning (why the adjustment was made)
  
Validation:
  Audit trail MUST be preserved; enable rollback/analysis of assessment history.
  
Status: Mandatory for any system that repeatedly assesses similar items.
```

### ZDB-AM-002: Dependency Topology Governance

**Source:** zombie_consumer.py (Import Graph Intelligence — Upgrade 2)

**SSOT Target:** Appendix G (new)

**Draft Text:**

```
APPENDIX G: Dependency Topology Analysis and Redundancy Governance

Goal: Establish canonical rules for module interdependencies, centrality ranking, and dedup authority.

1. Graph Representation
   - Nodes: Modules (imports); edges: dependency relations (module A imports module B).
   - Directed acyclic graph (DAG) assumed; cycles detected and escalated as warnings.
   
2. Centrality Metrics (NetworkX)
   - Degree centrality: How many modules depend on this module? (popularity)
   - Betweenness centrality: How often does this module appear in dependency paths? (criticality)
   - Weighted analysis: Ore rating of each consuming module adds weight to centrality.
   
3. Redundancy Scoring
   - Content hash (sha256) of module semantics.
   - If module A and module B have identical/near-identical content hashes, they are flagged as redundant.
   - Redundancy score ∈ [0, 1]; 1 = perfect duplicate.
   
4. Dedup Authority Chain
   - Primary: Content hash comparison (deterministic).
   - Secondary: Semantic similarity (if hash differs but content is near-identical).
   - Decision tree: Keep the module with highest centrality + lowest ore cost (maintenance burden).
   - Archive the redundant sibling to dumpster-dive/intake/.
   
5. Centrality-Based Priority Ranking
   - Modules with high betweenness centrality are "load-bearing."
   - Changes to load-bearing modules require elevated review.
   - Modules with low centrality and low ore are candidates for deferment/archival.
   
Example (Zombie Consumer Import Graph):
   - pathlib: degree 0.857, betweenness 0.119, seen in 3 files
   - sys: degree 0.857, betweenness 0.1429, seen in 3 files
   - argparse: degree 0.5714, betweenness 0.0159, seen in 2 files
   
   Priority ranking (load-bearing first):
     1. sys (highest betweenness)
     2. pathlib (high degree, solid betweenness)
     3. json (high degree, solid betweenness)
     4. argparse (moderate degree, low betweenness)
   
   If argparse has semantic redundancy with another CLI library, it's a candidate for dedup.

6. Validation Gate
   - Run graph analysis quarterly.
   - Flag new dependencies that increase betweenness centrality (confirm necessity).
   - Archive redundant modules with audit trail.
   
Status: Mandatory for polyglot projects with 50+ modules.
```

### ZDB-AM-003: Feedback-Driven Adaptive Learning System

**Source:** zombie_consumer.py (Forge Feedback Loop — Upgrade 3)

**Draft Text:**

```
X.6. Feedback-Driven Adaptive Learning Systems

Goal: Formalize systems that learn from operational outcomes.

Principle:
  Systems MUST measure predictions against reality. Errors are signal.

Mechanism:
  1. Predict: Assess inputs; generate expected outcome.
  2. Observe: Capture actual outcome (success/failure/error type).
  3. Compare: Identify mismatches between prediction and observation.
  4. Integrate: Incorporate mismatches into future heuristics.

Metric Definitions (Non-Overlapping):
  - outcomes_total: Count of distinct forge events observed in a cycle.
  - outcomes_matched: Events where prediction agreed with observation (correct predictions).
  - outcomes_error: Events where prediction disagreed with observation (incorrect predictions).
  - Invariant: outcomes_matched + outcomes_error = outcomes_total
  - learning_rate: outcomes_error / outcomes_total ∈ [0, 1]
    (Measures proportion of errors integrated per cycle — NOT cumulative.)

Thresholds:
  - learning_rate < 0.10: System stagnant; audit heuristics.
  - learning_rate ∈ [0.10, 0.50]: Normal adaptation.
  - learning_rate ∈ [0.50, 0.80]: High integration; healthy.
  - learning_rate > 0.80: Chaotic; stabilize or reset.

Validation:
  - Error integration MUST be traceable (audit trail per absorbed error).
  - Predictions and outcomes MUST be persisted for post-hoc analysis.
  - Rollback: If error batch integration introduces instability, revert to prior heuristic state.

Status: Mandatory for any system that makes outcome predictions.
```

### ZDB-AM-006: Polyglot Script I/O Encoding Canon

**Source:** Session 7 standardization (PYTHONIOENCODING=utf-8 universal lock)

**SSOT Target:** §XIV.4.2 (new subsection under Python Environment Management)

**Draft Text:**

```
14.4.2. I/O Encoding for Polyglot Scripts

Goal: Ensure all Python scripts on Windows emit UTF-8 stdout correctly, especially when using rich, emoji, or box-drawing characters.

Canon Rule (UNIVERSAL):
  EVERY uv run invocation targeting a Python script that produces output MUST set PYTHONIOENCODING=utf-8.
  
  Pwsh (canonical):
    $env:PYTHONIOENCODING = 'utf-8'; uv run scripts/<script>.py <args>
  
  Brush/bash (equivalent):
    PYTHONIOENCODING=utf-8 uv run scripts/<script>.py <args>
  
  Inline python -c usage:
    $env:PYTHONIOENCODING = 'utf-8'; uv run python -c "<code>"

Rationale:
  Windows console encoding differs from Linux/Mac POSIX defaults.
  Without PYTHONIOENCODING=utf-8, Python's sys.stdout encodes assuming console default (typically cp1252 on Windows).
  This causes mojibake for emoji, box-drawing characters, and extended Unicode.
  
  The # -*- coding: utf-8 -*- header at file top handles file *reading*; PYTHONIOENCODING handles stdout *writing*.
  Both are necessary.

Downstream Effects:
  - rich library: Tables, panels, text styling emit box-drawing characters; WITHOUT PYTHONIOENCODING, display corrupts.
  - zombie consumer graph command: NetworkX centrality output includes Unicode symbols; MUST be UTF-8.
  - Any script using emoji or non-ASCII output: MUST set PYTHONIOENCODING.

No Exception Clause:
  Setting PYTHONIOENCODING=utf-8 has NO downside on Windows or POSIX.
  It is strictly safe; apply universally.
  Do not defer based on script type or output assumption.

Validation:
  Test all new Python scripts on Windows with:
    $env:PYTHONIOENCODING = 'utf-8'; uv run scripts/<new-script>.py
  If output contains emoji or box-drawing, test *both* with and without PYTHONIOENCODING to confirm no mojibake.

Status: Canonical and mandatory for all production scripts.
```
