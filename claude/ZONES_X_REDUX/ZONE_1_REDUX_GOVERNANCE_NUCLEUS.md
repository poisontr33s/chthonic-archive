14.4. Runtime Selection for Browser Automation

Goal: Ensure reliable browser automation across polyglot runtimes on Windows.

Canon Rule:
  For browser automation (Playwright, Puppeteer, CDP-based), use Node.js + libuv.
  Rationale: libuv's mature Windows Named Pipes abstraction prevents IPC hangs and zombie processes.
  
Deferred:
  Bun (Windows): Pending stabilization of child_process IPC (as of 2026-03).
  Historical: Bun 1.3.x documented hangs at browser launch (ENOENT on named pipe paths).
  
Implementation Pattern:
  Package.json: "test:e2e": "node tests/playwright_suite.js"  (forces Node, not Bun)
  Alternative: MCP Server (Node-based, remote or containerized) to abstract IPC entirely.
  
Status:
  ✅ Validated on Windows 11 (2024-2026 session data)
  ⏳ Revisit when Bun releases Windows IPC stabilization advisory

### Z1-AM-005: Bidirectional Amendment Protocol (Phase 1.0)

**Source:** Zone 1 §6 (Narrative Architecture + SSOT Integration)

**SSOT Target:** Phase 1.0 (new section, master protocol)

**Draft Text:**

```
PHASE 1.0: BIDIRECTIONAL AMENDMENT PROTOCOL

Goal: The SSOT is not just a read-only holder. Content flows *outward* (authority) and *inward* (amendment).
This protocol formalizes the feedback loop: discovery → proposal → review → integration → cascade validation.

CYCLE FLOW:

[ Discovery Phase ]
  agents.py, scripts/, or session work identify content that should be canonical.
  Example: "We've validated that supernormal stimuli must follow constraint Z1-AM-004."
  Output: Unstructured observation, code comment, or session note.

[ Proposal Phase ]
  Amendment candidate is formalized into JSON structure:
  {
    "id": "Z1-AM-NNN",
    "title": "Title of Amendment",
    "source": "Where the discovery came from (code, session, research)",
    "target_section": "SSOT section path (e.g., 'X.3.7', 'Appendix D.3')",
    "text": "Proposed amendment text (markdown)",
    "rationale": "Why this should be canonical",
    "review_status": "DRAFT"
  }
  Location: `.mas_mcp/amendments/` (JSONL file, one amendment per line)

[ Review Phase ]
  User reviews amendment batch during session.
  User may:
    - Accept (amendment → APPROVED)
    - Modify (amendment updated in-place)
    - Defer (amendment → DEFERRED; will revisit later)
    - Reject (amendment → REJECTED; rationale recorded)

[ Integration Phase ]
  Approved amendments are written into SSOT holder by the user.
  Each integration is atomic (one amendment = one edit session).
  Amendment ID is included in commit message:
    "Integrate Z1-AM-004: Entity Design Constraints (supernormal stimulus governance)"

[ Cascade Validation Phase ]
  Post-integration:
    - `ssot_hash` detects SSOT drift (expected; amendment changed content)
    - `hash_journal` records event and git commit SHA
    - Binding test suite validates all cross-refs still resolve
    - Derivative indexes regenerate (SSOT_NAVIGATION_INDEX, SSOT_STRUCTURAL_INDEX)
  
  Success Condition: All tests pass; no new contradictions introduced.

GOVERNANCE RULES:

  1. Amendments must be *additive* or *enrichment-only*.
     Rewrites of existing canonical text are OUT OF SCOPE (frozen).
     (Change frozen content via a separate formal revision protocol TBD.)

  2. Amendment batches are processed in **sessions**, not ad-hoc.
     A "Zone 1 Integration Cycle" groups related amendments for coherent review.

  3. Amendment history is immortal.
     All amendments (approved, rejected, deferred) are retained in .mas_mcp/amendments/
     with timestamps and user acceptance/rejection rationale.

  4. The SSOT holder's "amendment date" is updated in the frontmatter.
     Example: "Last amendment integration: 2026-03-27 (Z1-AM-001,002,003,004,005)"

DEFINITION OF DONE (Phase 1.0):

  ✅ Amendment protocol formalized in SSOT (§Phase 1.0)
  ✅ `.mas_mcp/amendments/` directory and JSONL format defined
  ✅ Review/approval workflow documented
  ✅ Integration workflow documented
  ✅ First amendment batch (Zone 1) processed through full cycle
  ✅ ssot_hash + hash_journal adapted to track amendment integration
  ✅ Binding test suite updated to validate amendment coherence
```
