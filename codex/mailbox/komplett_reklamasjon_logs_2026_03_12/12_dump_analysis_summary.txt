Dump analysis summary

Method: parsed PAGEDU64 crash-dump headers directly. This validates the bugcheck code and parameters in the dump files even without WinDbg stack resolution.

High-level findings:
- All five files are valid PAGEDU64 Windows crash dumps.
- All five are dump type 4 (MiniDump).
- Three of the five dumps are PAGE_FAULT_IN_NONPAGED_AREA (0x50).
- One dump is KMODE_EXCEPTION_NOT_HANDLED (0x1E).
- One dump is 0x1000007F, the mini-dump alias of UNEXPECTED_KERNEL_MODE_TRAP (0x7F).
- The repeated 0x50 dumps all show parameter 2 = 0x10, which Microsoft documents as an execute operation on x64.
- The repeated 0x50 dumps all show parameter 4 = 0x2, which Microsoft documents as a not-present page-table condition.
- The 0x1E dump shows STATUS_ACCESS_VIOLATION (0xC0000005) with exception address 0x0. This means the kernel hit an access violation at a null instruction address; strong sign of low-level corruption/instability.
- The 0x7F/0x1000007F dump shows parameter 1 = 0x8, which Microsoft documents as a double fault. Microsoft says common causes are kernel stack overflow or hardware problems, especially memory.
- Across these five dumps there is no single recurring named third-party driver in the header data. The pattern is mixed kernel stop codes plus WHEA CPU parity events elsewhere in the logs, which is more consistent with hardware/platform instability than with one ordinary application fault.

Interpretation notes:
- 0x50 with execute-operation semantics means the kernel tried to execute from invalid/non-present memory. That is a stronger hardware/corruption signal than a simple bad data read.
- 0x1E with STATUS_ACCESS_VIOLATION at address 0x0 means the faulting instruction pointer/address is null. That is not a normal user mistake; it is kernel-level instability.
- 0x7F double fault is one of the most severe stop patterns and commonly points to hardware or stack corruption problems.
