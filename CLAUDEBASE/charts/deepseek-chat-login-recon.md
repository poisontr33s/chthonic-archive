# DeepSeek Chat Login Recon

This artifact defines the evidence required before Chthonic Deepcode implements a DeepSeek consumer chat-session provider.

The official developer API lane is already implemented through `DEEPSEEK_API_KEY` and bearer authentication against `https://api.deepseek.com`. That is not this lane.

This lane targets the consumer surface at `https://chat.deepseek.com/`.

## Current Verified Boundary

- DeepSeek official API docs publish API-key bearer authentication for the developer API.
- DeepSeek official API docs do not currently publish a third-party OAuth contract for coding agents.
- DeepSeek consumer chat login exists separately from developer API usage.
- Chthonic Deepcode must not invent OAuth endpoints, Google client IDs, token exchange paths, or internal chat routes.

## Required Evidence

Before implementation, capture the following without storing secret values:

- Login entry URL opened by `https://chat.deepseek.com/`.
- Identity provider used: Google, Apple, email, or other.
- Redirect or callback URL shape.
- Token exchange endpoint shape, if visible.
- Session storage mechanism: cookie, localStorage, sessionStorage, or in-memory token.
- Token names and header names, without values.
- Refresh endpoint or session renewal behavior, if visible.
- Chat request endpoint path and method.
- Chat streaming protocol: SSE, fetch stream, websocket, or other.
- Required non-secret headers.
- CORS/client restrictions relevant to VS Code extension usage.
- Terms or policy signal indicating whether automated client access is allowed.

## Implementation Gate

Only after the evidence exists:

- Add a new provider lane: `CHTHONIC_PROVIDER=deepseek-chat`.
- Add `deepseekChatToken` or `deepseekChatSession` to `initialize` only if a stable token/session format is proven.
- Keep TypeScript limited to browser login and SecretStorage.
- Keep Rust as owner of provider requests, streaming, plan parsing, snippets, permission checks, and rollback.
- Feature-flag this lane if it depends on private web internals.

## Non-Implementation Until Evidence

Do not:

- Embed a guessed Google client ID.
- Claim `chat.deepseek.com` supports third-party OAuth until observed or documented.
- Reuse `DEEPSEEK_API_KEY` as a chat-session token.
- Move AI calls into the VS Code TypeScript bridge.
- Store cookies or session tokens in repo files.

## Chrome DevTools MCP Route

Chrome DevTools MCP is the preferred repeatable capture route when available.

- MCP server: `chrome-devtools`
- Package: `chrome-devtools-mcp@latest`
- Source: `ChromeDevTools/chrome-devtools-mcp`
- Local config is generated by `scripts/mcp_write_local.ps1`.
- For login reconnaissance, use visible browser mode rather than headless mode.
- Usage statistics and update checks should be disabled in local MCP config.

Generate local MCP config:

```powershell
pwsh -NoProfile -File scripts\mcp_write_local.ps1 -GitHubMode copilot
```

Then restart the MCP client/agent so the new server is discovered.

## HAR Sanitizer

Use a browser HAR export only after secrets are sanitized.

Capture:

1. Open DevTools Network.
2. Preserve log.
3. Visit `https://chat.deepseek.com/`.
4. Complete the consumer login flow.
5. Send one harmless chat message if login succeeds.
6. Export HAR.

Sanitize:

```powershell
uv run scripts\deepseek_chat_recon_sanitize.py C:\path\to\deepseek-login.har --out CLAUDEBASE\charts\deepseek-chat-login-observed.md
```

The sanitizer keeps endpoint shapes, public OAuth query parameters, header names, methods, status codes, and response shapes. It redacts cookies, authorization headers, OAuth codes, and token-like fields.

Review the generated file before sharing or committing it.
