An extension that splices claude.ai's design surface into Claude Code — same auth, same window, same hot-reload muscle memory.

You moved to Max. You don't want to alt-tab to claude.ai for design work, and you don't want a second auth flow, a second status bar, or a second mental model on top of Claude Code. Claude Design contributes directly into Claude Code's view container, reuses its Pro/Max OAuth, and adds three new surfaces — a multi-file design canvas, a hot-reload preview, and an asset review pane — styled to match your chthonic-archive aesthetic (amber on near-black, custom icon theme, runic status bar). Bun is the package manager and bundler throughout. Hot reload is non-negotiable.

00 Executive summary

The shortest version of this plan.

If you only read one thing

6-minute read total
  1. You don't need a new auth path. Anthropic supports your Claude Max subscription inside Claude Code via OAuth. We piggy-back on that. Web-cookie replay against claude.ai is unsupported, brittle, and out of scope.
  2. Claude Design extends Claude Code — it does not duplicate it. Same view container, same auth, same model. We add three contributions: a Designs tree, an Asset Review tree, and a Preview/Tweaks webview. Nothing competes for activation, nothing requires a second login.
  3. Bun is the toolchain, end to end. bun install, bun build, bun test, bun --hot for preview dev mode. No node_modules tax during onboarding.
  4. The webviews are React + Tailwind + shadcn/ui. Generated artifacts default to the same stack, so the preview that ships in the extension is the same surface generated artifacts target. Zero impedance mismatch.
  5. About Max tokenomics: the Max plan grants higher session caps and Opus access. As far as I know there isn't a separate “Design” quota distinct from your chat quota — design and chat usage debit the same Max allowance. Flagged here as the one item to verify before launch, not as plan-foundation truth.
  6. Phased toward an installable MVP. Phase 1 is the artifact you can bun run package and sideload into your Insiders instance. Each subsequent phase ships on its own without forcing a republish.
01 The honest constraint

Tokenomics, OAuth, and what we are not going to do.

The motivating frustration is real: you're paying for Claude Pro, but the moment you open the official Claude Code extension on its default config you're on API billing. That's a real friction. Before we plan anything, let's name what's possible and what isn't, because the auth choice decides almost every other architectural decision downstream.

Option A · sanctioned

Claude Code Pro/Max OAuth

Claude Code supports a /login flow that opens the browser, OAuths against your Claude.ai Pro or Max subscription, and stores a refresh token locally. Inference then debits your subscription quota, not API credits.

Use this. It is the single supported, stable Pro-subscription-in-editor path.

stable sanctioned
Option B · unstable

Reuse claude.ai web cookies

Lift the session token out of claude.ai's cookies, replay it against the web endpoints. Looks tempting, briefly works.

Don't. The endpoints aren't a public contract; they rotate, CSRF/CSP hardening lands, the cookie format changes — and reselling/automating that surface violates Anthropic's TOS regardless of whether it's "your own account".

TOS brittle
Option C · fallback

Anthropic API key (BYOK)

The thing you already do not want. We expose this as an opt-in escape hatch for power users on team plans, rate-limit overflow, or environments where browser OAuth isn't available — but it is never the default.

opt-in only
!

The plan locks Option A as the primary path. Canvas does not ship its own OAuth client; it never sees your password; it never touches claude.ai cookies.

If Claude Code is installed and signed in, Canvas reuses its credentials. If it isn't, we surface a one-click Sign in with Claude (Pro) button that runs claude /login for you and waits for the callback.

02 Auth & inference flow

How a keystroke in VS Code becomes a Pro-quota completion.

The diagram below is the full happy-path flow for a single chat turn or artifact generation. The red dotted boxes are the things we never do — they are pinned in the diagram so reviewers can verify the architecture by what it doesn't touch as much as by what it does.

Fig 1 · Single-turn flow. Canvas owns steps 1, 5, 6. Anthropic-supported tooling owns 2–4.

Why claude CLI as the inference shim

It is the highest-stability surface Anthropic offers for "use Pro auth headlessly." Its --print --output-format=stream-json mode emits a documented JSON stream of message events, tool calls, and usage stats that we can pipe straight into the webview. Token refresh, retry, rate-limit backoff, and quota accounting are all problems the CLI solves for us.

Forward path: extension API surface

VS Code extensions can activate() and export a public API that other extensions consume via extensions.getExtension('anthropic.claude-code').exports. If Claude Code grows such a surface, Canvas should prefer it over CLI subprocess. We design the inference adapter as an interface so the swap is one file.

03 System architecture

Process model, boundaries, and what owns what.

VS Code extensions have a deceptively constrained shape: one Node.js process (the extension host) runs your TypeScript; every UI lives inside a sandboxed webview iframe; the only way they talk is postMessage. Canvas embraces that constraint instead of fighting it.

Fig 2 · Three webviews, one extension host, one subprocess. Five wires, all crossing one trust boundary each.

Trust boundaries

  • Webviews are sandboxed iframes — they get nothing from the host that isn't postMessage'd explicitly.
  • The CLI keystore is treated as opaque; we shell out, we don't parse it.
  • All file writes funnel through the FS broker, which enforces a workspace-relative path allowlist.
  • The preview iframe runs with sandbox="allow-scripts" only — no allow-same-origin.

What we deliberately don't build

  • An OAuth client. The CLI has one already.
  • A token refresher. The CLI has one already.
  • A model selector UI. We honor whatever Claude Code chose.
  • A per-extension settings store for API keys. There are no API keys.
  • Telemetry. Out of scope; we ship with it off, the user opts in via setting if ever.

05 Splicing into Claude Code

One extension, one window, zero second logins.

The shift from “sidecar” to “extends” is the highest-leverage decision in this revision. Claude Design declares extensionDependencies: ["anthropic.claude-code"] so it activates only when Claude Code is present, contributes its views into Claude Code's existing view container (falling back to its own when the host container ID isn't public), and reuses Claude Code's auth keystore through the same CLI shim. Below: the six contracts that make this safe.

contract 1

Disjoint command namespace

Every command starts with claudeDesign.; every label is Claude Design: …. Lives in the same palette as Claude Code, never shadows it.

contract 2

Disjoint settings & storage

Settings under claudeDesign.*. Workspace state in .claude-design/. Global state in workspaceState/globalState keyed design.. We never write Claude Code's keys.

contract 3

Shared OAuth, shared quota surface

Both extensions read the same ~/.claude/credentials via the CLI. Quota indicator lives in Claude Code's existing status item when its API allows; otherwise Design shows a sibling pill in matching amber.

contract 4

FS broker with conflict back-off

Design only watches .claude-design/** and designs/**. If Claude Code is mid-stream into a file Design wants to touch, we requeue with a 200ms backoff and surface a non-modal toast.

contract 5

Single sign-in doorway

If Claude Code is signed in, Design's sign-in UI never appears — we just work. If not, our welcome view says “Sign in via Claude Code” and triggers Claude Code's own command. We never run our own OAuth.

contract 6 · forward-looking

Programmatic handoff

When Claude Code exposes a public extension.exports, Design detects it on activate and swaps the CLI-subprocess adapter for an in-process call. No user-visible change. One file diff.

06 Workspace & design-system model

What lives on disk, what's read-only, and how cross-project mounts work.

The claude.ai habit you don't want disturbed: dropping a design system into a project as an attachment and letting it inform every output. In VS Code that's just a folder, but it has to be read-only, scoped, and visible to the model without being committed into your workspace. 

my-project/
├── designs/                # your output — html files, components
│   ├── Landing.html
│   ├── Pricing.html
│   └── components/
├── assets/                 # images, fonts, video
├── .canvas/                # Canvas's own scratch space
│   ├── manifest.json       # asset review state
│   ├── conversation.jsonl  # chat history (local only)
│   └── tweaks.json         # EDITMODE state per file
├── CLAUDE.md               # project rules — picked up automatically
└── canvas.code-workspace   # mounts a design-system folder read-only

Design-system mounts

VS Code's multi-root workspace gives us folder URIs. Canvas adds a virtual scheme canvas-ds:// that proxies a chosen folder anywhere on disk as read-only. The model sees it as canvas-ds://design-system/colors.css; it can read, it cannot write. This is the local equivalent of the cross-project read access you have on claude.ai.

Project rules (CLAUDE.md)

Same conventions as Claude Code — root CLAUDE.md auto-loads as a system-level instruction. Canvas adds a UI affordance: status-bar pill 📜 rules that opens it in a peek editor and shows a diff if it changed since the last turn.

FS broker — write rules

Tool calls from the model can only write under designs/, assets/, and .canvas/. Anything else triggers a confirmation prompt with the proposed path and content. This is enforced in the host, not the prompt.

Live reload & devices

Preview iframe is rebuilt on file save (workspace.onDidSaveTextDocument). User can wrap the preview in iOS / Android / browser frames via the same starter components used on claude.ai — Canvas ships those frames inline so they work offline.

07 Asset review & Tweaks parity

The two protocols that make claude.ai's design loop feel different from a chat box.

Asset review

The manifest lives at .canvas/manifest.json: an array of {asset, path, status, group, viewport, subtitle}. Canvas writes it; the user marks status from the side-bar TreeView; the model reads it on every turn so it knows what's pending.

{
  "items": [
    {
      "asset": "Landing page",
      "path": "designs/Landing.html",
      "group": "Components",
      "status": "needs-review",
      "viewport": { "width": 1440 }
    },
    {
      "asset": "Brand colors",
      "path": "designs/colors.html",
      "group": "Colors",
      "status": "approved"
    }
  ]
}

Side-bar TreeView groups by group. Right-click an item to open with viewport pinning. Bulk approve across selection. Status changes are debounced to manifest.json writes so the file diff stays clean.

Tweaks protocol

The same __edit_mode_* postMessage protocol claude.ai uses, ported as-is so any HTML you wrote on claude.ai keeps working in VS Code with zero changes.

// the artifact says:
window.parent.postMessage({type:'__edit_mode_available'}, '*');

// Canvas reveals a toolbar toggle.
// User flips it on:
window.postMessage({type:'__activate_edit_mode'});

// User changes a knob:
window.parent.postMessage(
  {type:'__edit_mode_set_keys', edits:{primary:'#D97757'}},
  '*'
);

// Canvas merges into the EDITMODE-BEGIN/END
// JSON block in the source HTML, saves to disk.

Persistence is the trick: Canvas parses the /*EDITMODE-BEGIN*/…/*EDITMODE-END*/ block, merges the partial edits, and rewrites the file in place. The change survives reload because it survives save.

08 Implementation phasing

Five phases. Each one is independently shippable.

The point of phasing is that you can stop after any phase and have a useful tool. We don't bury value behind a 12-week build — phase 1 alone gets the live preview into VS Code with Pro auth, which is the lion's share of the daily-driver experience.

PHASE 0
~3 days

Skeleton & auth

Empty extension, activates on a single command, surfaces a side-bar webview that says "Hello, signed-in user." Underneath: inference adapter interface, CLI subprocess wired up, OAuth check on activation, status bar item, settings schema.

activate / deactivate claudeCanvas.signIn CLI adapter v1 status bar
PHASE 1
~1 week

Chat + preview

Chat panel that streams responses. Tool-use messages that write HTML files into designs/. A preview webview beside the editor that loads the most recent artifact via srcdoc with live reload on save. This is the MVP — already replaces 70% of why you'd alt-tab to claude.ai.

chat panel stream-json parser FS broker preview surface live reload
PHASE 2
~3 days

Asset review

Side-bar TreeView for the manifest. Status icons, group filters, bulk-approve. Manifest read by the model every turn so "what's pending" is always accurate.

manifest schema review TreeView status quick-pick
PHASE 3
~4 days

Tweaks & mention bridge

Full __edit_mode_* protocol parity. Inline element comments / mentions surface in the chat panel as <mentioned-element> attachments. Drag-and-drop a workspace file into chat to mention it.

edit-mode bridge EDITMODE rewriter mention picker
PHASE 4
~3 days

Cross-project · design-system mounts

canvas-ds:// virtual scheme. Read-only proxy of any folder. canvas.code-workspace generator that bakes a chosen design-system path in. Asset review respects the mount so DS files never accumulate review state.

FileSystemProvider workspace generator mount UI
PHASE 5
~3 days

Polish & release prep

Marketplace listing, Insiders-targeted engines.vscode, telemetry-off-by-default, a CONTRIBUTING.md for handoff, performance pass on the preview iframe (it should redraw <100ms after save). Verify all six sidecar contracts with integration tests.

09 Risk register

Things that can break this plan, ranked.

RiskSeverityMitigation
CLI surface changes. claude --print --output-format=stream-json isn't a frozen API contract. MEDIUM Adapter interface isolates the contract to one file. Pin a known-good CLI version range. Run a contract test on activation that warns if the JSON shape drifts.
Pro/Max OAuth scope changes — Anthropic could decide editor clients need a different scope or a separate consent. HIGH We never bypass; if the CLI says "re-auth", we surface that prompt verbatim. We don't ship our own client_id.
Webview CSP and resource roots. The preview iframe needs to load workspace files; VS Code's CSP is strict. MEDIUM Use asWebviewUri for asset references. Use localResourceRoots scoped to designs/ + assets/. Keep iframe sandbox to allow-scripts only.
Race conditions with Claude Code on the same file. MEDIUM FS broker holds an in-memory lock per path. If a save lands within 200ms of another writer, we requeue and notify. Tests cover concurrent-write scenarios.
User has no Claude Code installed and no terminal experience. LOW Canvas can ship with a bundled claude CLI binary on first install (Windows/macOS/Linux), or run claude /login via integrated terminal with on-screen guidance.
Quota exhaustion mid-session. Pro plans have 5-hour blocks; running out is jarring. LOW Status bar shows live % used. At 80% we surface a non-blocking toast; at 100%, chat input gets disabled with the same wording claude.ai uses.
Insiders-only API drift. Targeting Insiders means we can use proposed APIs but we have to track them. LOW Limit proposed API usage to one feature (likely chatVariableResolver or similar) and gate it behind a feature flag.
