# SSOT Name Repair Doctrine

## Core Rule

If an entity's earliest established name is bound to the abbreviation system, subsystem naming, invocation grammar, or SSOT cross-reference lattice, that earliest name is canonical.

Later Local-AI-assisted renames, metadata injections, compressed aliases, or decorative substitutions do not become canon by mere existence.

They are drift until explicitly ratified by the user.

## Interpretation

- Core names are the load-bearing identity layer.
- Abbreviations and subsystem names derive from the core names.
- If the core name drifts, the abbreviation system loses meaning.
- Therefore canon repair must prefer the earliest abbreviation-bound name unless the user explicitly replaces it.

## Allowed Layers

- Canon name:
  The load-bearing identity used by SSOT, abbreviations, subsystem references, and entity law.
- Secondary epithet:
  A descriptive subtitle or dark-humour expansion that may accompany the canon name.
- Drift variant:
  A later rename, shorthand, or injected metadata form that does not carry canonical authority.

## Repair Order

1. Repair the SSOT archive and canonical satellites first.
2. Repair scripts and archaeology tooling second.
3. Repair derivative docs, references, and lore mirrors third.
4. Preserve drift variants as searchable archaeology, not as canon.

## Constraint

Do not replace canon names with shorthand labels in any system that depends on:
- abbreviations
- subsystem names
- invocation syntax
- cross-reference anchors
- hierarchy tables

## Operational Consequence

When a name conflict appears:
1. Find the earliest abbreviation-bound form.
2. Check whether the user explicitly ratified a replacement.
3. If not ratified, revert to the earliest canonical form.
4. Preserve later variants as drift metadata only.
